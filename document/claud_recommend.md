**เอกสารที่ตรวจ:** `checklist.md` (Checklist กลาง) เทียบกับ `StoryFlow-Game-Studio-Concept.md` (v2)
**วัตถุประสงค์:** ตอบคำถามว่า Checklist ครบถ้วนหรือไม่ และควรเพิ่มหรือแก้อะไร พร้อมข้อความที่นำไปวางใน Checklist ได้ทันที
**ข้อจำกัดของการตรวจ:** ไม่ได้รับไฟล์ `AGENTS.md` ที่ Checklist อ้างถึง จึงตรวจกติกาการทำงานของ agent (ช่องพัฒนา/ตรวจรับ, บันทึกของ agent) ได้เพียงจากที่ Checklist เขียนไว้เอง ข้อมูลเรื่อง Ren'Py CLI ในเอกสารนี้อ้างอิงเอกสาร Ren'Py ที่ค้นได้ ยังไม่ได้ทดลองรันกับ SDK รุ่นที่จะตรึง

## 1. สรุปคำตอบ

**Checklist ยังไม่ครบถ้วน แต่โครงสร้างดีและครอบคลุมส่วนใหญ่ของ Concept**

จากการไล่ 30 ข้อกำหนดของ Concept เทียบกับงานใน Checklist:

| ผลการเทียบ | จำนวน | ความหมาย |
|---|:---:|---|
| ครบ | 20 | มีงานและเกณฑ์ตรวจรับรองรับตรง |
| บางส่วน | 8 | มีงานแต่เกณฑ์ไม่ครบหรือวัดไม่ได้ |
| ไม่มี | 2 | ไม่มีงานรองรับเลย |

ปัญหาที่สำคัญกว่าการตกหล่นรายข้อมี 4 กลุ่ม:

1. **ความเสี่ยงสูงสุดของโครงการยังไม่มีงานพิสูจน์ก่อนเริ่ม** คือการรัน Ren'Py แบบอัตโนมัติและดึง Trace กลับมา Gate 0a ทั้งหมดพึ่งสิ่งนี้ แต่ `0a.1` ให้ "ตัดสินใจ" วิธีเก็บ Trace ก่อนจะมีใครลองทำได้จริง
2. **เกณฑ์ตรวจรับหลายข้อวัดไม่ได้** เช่น "ครบทุกกรณี", "ทุกกรณีจำลองความล้มเหลว", "ตรงกัน 100%" โดยไม่มีรายการกรณีหรือรายการกฎที่นับได้
3. **Concept กับ Checklist ไม่ตรงกันในบางจุด** (ดูข้อ 6) รวมถึงรายการ "Sandbox/ZIP" ใน Checklist ที่ไม่มีใน Concept
4. **Phase 2 วัดสิ่งที่ Phase 1 ไม่ได้สร้าง** คือเป้า "ผู้ใช้ใหม่ทำฉากแรกได้ภายใน 30 นาที" ทั้งที่ไม่มีงาน onboarding, ตัวอย่างโปรเจกต์ หรือกำหนดภาษาของ UI

## 3. ข้อค้นพบเรียงตามความสำคัญ

**ระดับ:** P0 = แก้ก่อนเริ่ม Phase 0a, P1 = แก้ก่อน Gate ของ Phase นั้น, P2 = ปรับปรุงเพื่อความชัดเจนและความเสี่ยงต่ำ

### P0 — แก้ก่อนเริ่ม Phase 0a

#### R1 · ยังไม่มีงานพิสูจน์ว่ารัน Ren'Py อัตโนมัติและเก็บ Trace ได้

**ปัญหา:** Concept และ Checklist เรียกการเทียบกับ Ren'Py ว่า "SDK Headless" แต่ไม่มีงานไหนพิสูจน์ว่าทำได้ และ `0a.1` กำหนดให้ "ตัดสินใจวิธีเก็บ Trace จาก SDK" ก่อนจะมีใครลองทำ ทำให้ลำดับงานวนกลับ (ต้องตัดสินใจก่อนลอง แต่ต้องลองก่อนจึงตัดสินใจได้)

**สิ่งที่ตรวจพบจากเอกสาร Ren'Py:** Ren'Py มีคำสั่ง CLI `lint` และ `test` (รัน testcase อัตโนมัติ) ใช้ใน CI ได้ ตัวอย่าง CI ที่พบใช้ `SDL_VIDEODRIVER=dummy` กับ `lint` ส่วนเครื่องมือที่ควบคุมเกมที่กำลังรัน (เช่น RenForge) ระบุว่าต้องมีหน้าจอหรือ `xvfb-run` แปลว่า "headless" ไม่ใช่โหมดที่รับประกันมาให้ ต้องพิสูจน์ว่าคำสั่ง `test` หรือวิธีอื่นรันได้บนเครื่อง CI ของโครงการ

**ข้อเสนอ:** เพิ่มงาน `0a.0` ก่อน `0a.1` ดูข้อ 4.1 ทางเลือกที่ควรทดลองในงานนี้:

| ทางเลือก | แนวคิด | ข้อควรระวัง |
|---|---|---|
| ก. Instrumentation ใน `sf_runtime.rpy` | โค้ดที่สร้างเขียน Trace เป็น JSON Lines ลงไฟล์ทุกก้าว | ต้องไม่เปลี่ยนพฤติกรรมเกม (R5) |
| ข. Ren'Py `test` testcase | สคริปต์ทดสอบเลือกตัวเลือกแล้วตรวจสถานะ | เลือกตัวเลือกด้วยข้อความได้ แต่การดึงค่าตัวแปรและ Event ทุกก้าวต้องพิสูจน์เพิ่ม |
| ค. ตัวขับอินพุตใน runtime | โหมด debug อ่านชุดอินพุต JSON แล้วเลือกให้อัตโนมัติ | ต้องปิดในเกมจริง |

เกณฑ์ผ่านของ spike: รันเกมทดสอบ 1 ฉากบนเครื่อง CI เป้าหมายโดยไม่ต้องมีคนกด และได้ไฟล์ Trace อย่างน้อยหนึ่งก้าวกลับมา

#### R2 · ไม่มีกติกาตัดสินเมื่อ Core กับ Ren'Py ให้ผลต่างกัน

**ปัญหา:** `0a.6` ระบุ "เก็บผลต่างที่พบจนแก้ครบ" แต่ไม่ระบุว่าใครถูก ถ้า Core ตีความต่างจาก Ren'Py อาจแก้ผิดฝั่งเพื่อให้ตรงกัน

**ข้อเสนอ:** กำหนดว่า **สเปกใน Concept เป็นผู้ชี้ขาด** ไม่ใช่ Core และไม่ใช่ Ren'Py เมื่อผลต่างกัน ให้ตรวจเทียบสเปก: ถ้าฝั่งใดผิดสเปก แก้ฝั่งนั้น ถ้าสเปกกำกวมให้บันทึกเป็นข้อสงสัยและส่งให้เจ้าของโครงการตัดสิน แล้วปรับ Concept และ fixture ก่อนแก้โค้ด

#### R3 · เกณฑ์ "ครบทุกกรณี" วัดไม่ได้

**ปัญหา:** `0a.4` ระบุ "ตรวจจับ Error/Warning จาก Fixture ทดสอบได้ครบทุกกรณี" แต่ `0a.2` ให้ fixture เฉพาะกลุ่ม A และ A+ (กรณีที่ผ่าน) ไม่มี fixture ที่ผิดโดยตั้งใจ และไม่มีรายการกฎที่ต้องตรวจ จึงไม่รู้ว่า "ครบ" คือกี่ข้อ

**ข้อเสนอ:** สร้าง **รายการกฎ Validator พร้อมรหัส** (เช่น V-001…) ทุกกฎมี fixture ผิด 1 ชุด (ต้องถูกจับ) และ fixture ถูก 1 ชุด (ต้องไม่ถูกจับ) และมี **ตารางครอบคลุม** ว่าโหนดทั้ง 5 ชนิดและกฎทุกข้อใน §3.5–§3.7 ปรากฏใน Trace อย่างน้อย 1 กรณี เกณฑ์ตรวจรับเปลี่ยนเป็น "ทุกรหัสกฎมีคู่ fixture ผ่านและไม่ผ่าน และตารางครอบคลุมไม่มีช่องว่าง" กฎขั้นต่ำจาก Concept ที่ควรอยู่ในรายการ:

| กลุ่ม | กฎ |
|---|---|
| Subgraph | ทุกเส้นทางจบที่ `return`/`ending`; ห้าม `jump`; ห้าม `schedule` ซ้อน |
| Scene | scene ที่มี choices ต้องต่อพอร์ต `fallback`; ไม่มี choices ต้องต่อ `next` |
| Event | `priority` และ `order` ซ้ำในเฟสเดียวกัน; `once` ถูกบันทึกก่อนเข้า Subgraph |
| Schedule | พอร์ต `onComplete` ต้องต่อ; ต้องมี Fallback Activity ที่ไม่มีเงื่อนไข |
| ตัวแปร | ชนิดและช่วงค่าเริ่มต้น/operand; เทียบผิดชนิดใน Condition AST |
| อ้างอิง | ID สูญหาย; พอร์ตถูกตัดขาด; พาธสื่อ |
| Loop Guard | วนอัตโนมัติเกินเพดานแล้วหยุดและรายงานโหนด |
| ชื่อ | ชื่อ `sf_<kind>_<shortId>` ชนกัน |

#### R4 · Summer House ชุดเดียวไม่พอพิสูจน์ "Parity 100%"

**ปัญหา:** Gate 0a พิสูจน์ความตรงกันจากกรณีที่เขียนมือไม่กี่กรณี Summer House 6 กรณีนี้อาจไม่แตะ Schedule `onComplete`, Event priority ชน, Subgraph ซ้อนหลายชั้น, `branch` แบบ `all/any/not`, หรือ Loop Guard ความตรงกัน 100% บนกรณีที่เลือกไว้จึงไม่ได้แปลว่าตรงกันทุกกรณี

**ข้อเสนอ:** เพิ่มงาน `0a.6b` Differential fuzzing: สร้างกราฟขนาดเล็กแบบสุ่มด้วย seed คงที่ รันทั้ง Core และ Ren'Py ด้วยอินพุตชุดเดียวกัน แล้วเทียบ Trace กำหนดเกณฑ์เป็นจำนวนกราฟต่อรอบ (เช่น ชุดเล็กเป็น Gate และชุดใหญ่รันกลางคืนใน CI) ผลต่างทุกครั้งต้องย่อเป็น fixture ถาวรและแก้ตาม R2

#### R5 · Trace instrumentation ต้องไม่เปลี่ยนพฤติกรรมและไม่ติดไปกับเกม

**ปัญหา:** ถ้าเก็บ Trace ด้วยโค้ดใน `sf_runtime.rpy` (ทางเลือก ก. ใน R1) โค้ดนั้นอาจเปลี่ยนพฤติกรรม (เช่น ทำให้ rollback หรือ Save ผิดปกติ) หรือหลุดไปในเกมที่แจกจ่าย Checklist ไม่มีเกณฑ์เรื่องนี้

**ข้อเสนอ:** เพิ่มเกณฑ์ใน `0a.5`: (1) instrumentation เปิดได้เฉพาะเมื่อตั้งค่า debug ชัดเจน และปิดเป็นค่าเริ่มต้น (2) เกมที่ส่งออกปกติไม่มีโค้ดหรือไฟล์ Trace (3) ผลเกมเหมือนกันเมื่อเปิดและปิด instrumentation สำหรับอินพุตเดียวกัน (เทียบตัวแปรสุดท้ายและฉากจบ)

#### R6 · สเปกที่ยังไม่ล็อกแต่กระทบ fixture

ข้อเหล่านี้ควรตัดสินใน `0a.1` ก่อนเขียน fixture ไม่เช่นนั้น fixture จะต้องแก้ทีหลัง

| # | ประเด็น | เหตุผล |
|---|---|---|

| e | **การไม่มี random** ระบุให้ชัดว่า runtime ที่สร้างไม่เรียกฟังก์ชันสุ่มและ Validator ไม่มีโหนดสุ่ม (แถวที่ 13) | เพื่อให้ Trace deterministic |

#### R7 · Gate 0a ผูกกับงานที่ไม่ใช่ Parity และตารางเวลาเสี่ยง

**ปัญหา:** Gate 0a ต้องผ่านทั้ง Parity, SDK/fixture ที่ตรึง และ baseline ขณะที่ `0a.3` รวม Undo/Redo, migration, property test และ `0a.7` ต้องทำ WASM/Worker รวมแล้ว 7 งานใน ~2 สัปดาห์ ถ้า Parity ติดปัญหา (R1) งานที่ไม่เกี่ยวกับ Parity จะถูกเร่งหรือถูกตัด

**ข้อเสนอ:** แยกเป็นสองทางในเอกสาร: **ทางหลัก (Parity)** คือ 0a.0 → 0a.1 → 0a.2 → 0a.3 (เฉพาะโมเดล, ID, effect/clamp, AST) → 0a.4 → 0a.5 → 0a.6 ส่วน **ทางคู่ขนาน** คือ Undo/Redo ระดับ Command, migration และ WASM/baseline ให้ Gate 0a อ้างเฉพาะทางหลัก ส่วนทางคู่ขนานต้องเสร็จก่อน Gate 0b เจ้าของโครงการควรยืนยันว่าตารางเวลา 0a ~2 สัปดาห์สมเหตุสมผลกับจำนวนผู้พัฒนาจริง

### P1 — แก้ก่อน Gate 0b และ Gate 1

#### R8 · การส่งออกไม่ถูกระบุว่าต้องถูกบล็อกเมื่อมี Validation Error

Concept §3.7 ระบุว่า Event ซ้ำเป็น Error และ **บล็อกการส่งออก** แต่ `1.6` ไม่มีเกณฑ์ข้อนี้ เพิ่มเกณฑ์: ส่งออกไม่ได้เมื่อมี Error (แสดงรายการและพาไปโหนดต้นเหตุ) ส่งออกได้เมื่อมีแค่ Warning พร้อมแสดงรายการ นอกจากนี้ Concept §3.10 ระบุให้ **หยุด** เมื่อ hash ต่างจากที่ระบบเคยสร้าง ขณะที่ Concept ฉบับเดิมให้ **แจ้งเตือนก่อนเขียนทับ** ต้องให้เจ้าของโครงการตัดสินว่าผู้ใช้ทำอะไรได้หลังระบบหยุด (ดูรายละเอียดต่าง, สำรองแล้วเขียนทับ, ยกเลิก) เพราะ `1.6` ต้องมี UI สำหรับเรื่องนี้

#### R9 · Escaping ไม่ครอบคลุมทุกบริบท และยังไม่มีการป้องกันข้อมูลอันตราย

**ปัญหา:** Concept §3.10 ให้ Escape ครอบคลุมบทสนทนา ชื่อตัวเลือก ชื่อตัวละคร และค่า `string` แต่ `0b.3` ทดสอบอักขระพิเศษแบบ literal โดยไม่ระบุว่าทดสอบทุกจุด นอกจากนี้ Ren'Py รันโค้ด Python ได้ ค่า `string` และชื่อที่ผู้เขียนพิมพ์จึงอาจถูกใส่ลงในโค้ด Python ที่สร้าง (เช่น ค่าเริ่มต้นของตัวแปร) ซึ่งใช้กฎ Escape **คนละชุด** กับข้อความที่แสดง ถ้าไฟล์โปรเจกต์มาจากคนอื่น ข้อความที่แทรกเครื่องหมายคำพูดและคำสั่งอาจรันโค้ดบนเครื่องผู้ใช้ตอนเล่นเกมที่ส่งออก

**ข้อเสนอ:** เพิ่มงาน `0b.6` ทดสอบความปลอดภัยของการสร้างโค้ด:

| บริบท | จุดที่ต้องทดสอบ | อินพุตทดสอบ |
|---|---|---|
| ข้อความ Ren'Py | บทสนทนา, ชื่อตัวเลือก, ชื่อตัวละคร | `[ ] { } % " \` และอักขระไทยผสม |
| สตริง Python | ค่าเริ่มต้นตัวแปร `string`, ค่า `set` | `"`, `\`, ขึ้นบรรทัดใหม่, `"""`, ลำดับที่ปิดสตริงแล้วต่อด้วยคำสั่ง |
| ตัวระบุ (identifier) | label, ชื่อตัวแปร | ชื่อเป็นภาษาไทย, ช่องว่าง, คำสงวนของ Python/Ren'Py |
| ไฟล์โปรเจกต์ | Parser ของ `project.storyflow.json` | Condition AST ซ้อนลึกมาก, ไฟล์ขนาดใหญ่ผิดปกติ, จำนวนโหนดเกินเพดาน |

เกณฑ์: ทุกอินพุตผ่านการสร้างและเปิดใน SDK โดยไม่แครชและไม่รันโค้ดที่ไม่ได้ตั้งใจ Parser ปฏิเสธไฟล์เกินเพดานความลึก/ขนาด/จำนวน อย่างสุภาพ (แจ้งข้อผิดพลาด ไม่ค้าง) กำหนดเพดานเหล่านี้ใน Contract

#### R10 · การสร้างไฟล์ต้องให้ผลซ้ำได้ (deterministic)

ถ้าโปรเจกต์เดิมส่งออกซ้ำแล้วได้ไฟล์ไม่เหมือนเดิมทุกไบต์ (ลำดับไม่คงที่ เวลาประทับ ตัวคั่นบรรทัดต่างกัน) hash ใน manifest จะเปลี่ยนโดยไม่มีใครแก้ไฟล์ ทำให้เตือนผิดและทดสอบกลุ่ม C ไม่น่าเชื่อถือ เพิ่มเกณฑ์ใน `0a.5` และ `0b.4`: (1) โปรเจกต์เดิมส่งออกซ้ำแล้วไบต์เหมือนเดิมทุกไฟล์ (2) กำหนด UTF-8 ไม่มี BOM และตัวคั่นบรรทัดคงที่ (LF) (3) ผลตรงกันเมื่อรันบน Windows และ Linux เพราะผู้ใช้กลุ่มเป้าหมายอาจใช้ Windows เป็นหลัก

#### R11 · `0b.2` ใหญ่เกินไปและเกณฑ์ Source Map กำกวม

`0b.2` รวม Transaction, สำรอง, pending journal, กู้คืน, Source Map และ Warning เรื่อง Save ในงานเดียว ทั้งที่เกณฑ์ตรวจรับเขียนว่า "ทำงานตาม §3.10" ซึ่งตรวจไม่ได้ ข้อเสนอ: แยกเป็น `0b.2a` Transaction และกู้คืน, `0b.2b` Source Map, `0b.2c` Warning Save เกณฑ์ที่วัดได้ของ `0b.2b`: ใส่ข้อผิดพลาดจงใจลงในสคริปต์ที่สร้าง รัน `lint` ของ Ren'Py แล้วนำเลขบรรทัดในรายงานไปย้อนกลับด้วย Source Map ต้องได้ `nodeId` ของโหนดต้นเหตุตรงทุกกรณี และต้องจัดการกรณีที่บรรทัดอยู่นอกช่วงที่แมปได้ (เช่น บรรทัดใน `sf_runtime.rpy`) โดยแจ้งอย่างเหมาะสม

#### R12 · สิ่งที่ต้องพิสูจน์ใน `0b.1` ว่าทำได้จริงบนเบราว์เซอร์

Concept ตั้งสมมติฐานเกี่ยวกับ File System Access API หลายข้อที่ควรทดลองก่อนสร้าง Transaction บนฐานนี้ (ผมไม่ได้ทดสอบ ต้องพิสูจน์กับ Chrome/Edge รุ่นเป้าหมาย):

| สมมติฐาน | สิ่งที่ต้องพิสูจน์ | ถ้าไม่เป็นจริง |
|---|---|---|
| เขียนไฟล์แบบ atomic ต่อไฟล์ | พฤติกรรมของการเขียนเมื่อปิดสตรีมไม่สมบูรณ์ | ปรับ journal ให้ครอบคลุมระดับไฟล์ |
| ปฏิเสธ symlink ที่ชี้ออกนอกโปรเจกต์ (§3.3) | เบราว์เซอร์เห็นและตรวจ symlink ได้หรือไม่ | ปรับถ้อยคำ Concept ให้ตรวจเฉพาะสิ่งที่ตรวจได้ |
| Ren'Py/Launcher เปิดไฟล์ค้างอยู่ระหว่างส่งออก | เขียนทับไฟล์ที่โปรแกรมอื่นเปิดอยู่บน Windows | ตรวจจับและแจ้งผู้ใช้แทนการล้มเหลวเงียบ ๆ |
| โฟลเดอร์ที่ซิงก์ผ่าน OneDrive/Dropbox/Google Drive | ไฟล์ถูกซิงก์ล่าช้า สร้างไฟล์ conflict หรือแก้ไฟล์ระหว่างเขียน | เพิ่ม Warning ตอนเปิดโฟลเดอร์ซิงก์ และทดสอบ revision check |
| Web Locks กันได้ | กันได้เฉพาะแท็บในเบราว์เซอร์เดียวกัน ไม่กันเบราว์เซอร์/โปรไฟล์/เครื่องอื่นที่เปิดโฟลเดอร์เดียวกัน | พึ่ง revision check (§3.11) และเพิ่มกรณีทดสอบสองเบราว์เซอร์ |
| สิทธิ์โฟลเดอร์ | ต้องขอใหม่เมื่อเปิดครั้งใหม่ และอาจหลุดกลางงาน | ตามที่ §3.11 ระบุแล้ว ต้องมีกรณีทดสอบจริง |

#### R13 · เป้าประสิทธิภาพ UI ล็อกใน `0b.5` ไม่ได้

`1.7` กำหนดให้ตัวเลขประสิทธิภาพผ่านเกณฑ์ที่ล็อกใน `0b.5` ซึ่งทำก่อนมี UI จริง จึงมีแต่ตัวเลขของ Core ส่วนการวาดกราฟ 2,000 โหนดด้วย React Flow และพรีวิวคลิปไม่มี baseline Concept §4.3 แยกชุด UI ไว้แล้วแต่ Checklist ยังไม่ตามให้ทัน ข้อเสนอ: เพิ่มงาน `1.0` ต้น Phase 1 ทำ spike วัดการวาดกราฟขนาดอ้างอิงและพรีวิวคลิป แล้วล็อกเป้า UI ก่อนเริ่ม `1.2` และแก้ `1.7` ให้อ้างเป้าสองชุด (Core จาก `0b.5`, UI จาก `1.0`)

#### R14 · ไม่มีงานวัด "แก้ฉาก → ส่งออกซ้ำ"

Concept §4.3 ระบุให้กำหนดเป้านี้จาก baseline ของ Phase 0 `0b.5` อ้างถึงเวลานี้ แต่ `0a.7` (วัดก่อนมี Exporter) ไม่ครอบคลุม และ `0b.2` ไม่มีงานวัดต่อ เพิ่มการวัดใน `0b.2a`: เวลาจากแก้ฉาก 1 ฉากในโปรเจกต์ 2,000 โหนดถึงส่งออกซ้ำเสร็จ (รวมการเขียนไฟล์และ journal)

#### R15 · ไม่มีงาน onboarding แต่ Phase 2 วัดเวลา 30 นาที

เป้า "ผู้ใช้ใหม่สร้างฉากแรกจนรันใน Ren'Py ภายใน 30 นาที" ขึ้นกับสิ่งที่ Phase 1 ยังไม่มีงานสร้าง ได้แก่ โปรเจกต์ตัวอย่าง (เช่น Summer House เป็นเทมเพลต), คำแนะนำครั้งแรก, ข้อความ Validator ที่อ่านเข้าใจ และคำอธิบายขั้นตอนเชื่อม entry label สำหรับเกมเดิม ยังไม่มีการระบุภาษาของ UI (Concept ใส่ Localization ไว้ Phase 3) ข้อเสนอเพิ่ม `1.8`: ตัวอย่างโปรเจกต์, คู่มือเริ่มต้นแบบสั้น, ข้อความแจ้งผิดพลาดเป็นภาษาที่ตัดสินแล้ว

#### R16 · การจัดการสื่อและพาธสื่อยังหยาบ

`1.2` ระบุเพียง "จัดการตัวละครและสื่อ" ขาดเกณฑ์เรื่อง: วิธีนำสื่อเข้าโฟลเดอร์ `game/assets/`, สื่อที่ขาดหรือถูกเปลี่ยนชื่อ, ชื่อไฟล์ซ้ำ และปัญหาที่เจอบ่อยกับ Ren'Py คือชื่อไฟล์ที่ต่างกันเฉพาะตัวพิมพ์ใหญ่เล็ก ช่องว่าง หรืออักษรไทยในพาธ ซึ่งทำงานต่างกันตามระบบปฏิบัติการ (ควรตรวจกับเอกสาร Ren'Py ของรุ่นที่ตรึง) ข้อเสนอ: เพิ่ม Warning ใน Validator สำหรับพาธที่เสี่ยง (ตัวพิมพ์ไม่ตรงกับไฟล์จริง ช่องว่าง อักขระนอก ASCII) และเกณฑ์ใน `1.2` สำหรับนำเข้า ตรวจสื่อหาย และชื่อซ้ำ

#### R17 · ไม่มีงานสร้าง CI และความทำซ้ำได้

Concept §3.9 ให้ CI ตรึงรุ่น SDK และ `0a.1` ให้เลือกรุ่นย่อย แต่ไม่มีงานสร้าง pipeline เกณฑ์ที่ควรมีใน `0a.8`: ตรึง SDK ด้วยหมายเลขรุ่นและ checksum (และแคช), ตรึง Rust toolchain และ lockfile, เก็บ hash ของ fixture, รันอย่างน้อยบน Linux และ Windows เพราะเรื่องพาธและตัวคั่นบรรทัด, และรัน Parity อัตโนมัติทุกครั้งที่แก้ Core หรือตัวสร้างโค้ด ควรตรวจรุ่น Ren'Py ล่าสุดที่เสถียรตอนตรึง เพราะ Gemini เสนอสาย 8.3.x ซึ่งผมไม่ได้ตรวจว่ายังเป็นรุ่นที่เหมาะสม ณ ตอนนี้

#### R18 · นโยบายสำรองข้อมูลและพื้นที่เก็บของเบราว์เซอร์

Concept (§3.1 เดิม) กล่าวถึงสำรองหมุนเวียน แต่ไม่มีนโยบายเก็บกี่ชุด ขนาดเท่าไร และ `1.5` ไม่ทดสอบกรณี IndexedDB เต็มโควตาหรือถูกเบราว์เซอร์ล้างข้อมูล ข้อเสนอ: กำหนดจำนวนและอายุสำรอง และเพิ่มกรณีทดสอบโควตาเต็ม/ถูกล้างใน `1.5` โดยต้องแจ้งผู้ใช้ชัดเจนและไม่ทำให้ Autosave ลงดิสก์หยุดทำงาน

| ข้อบกพร่อง | บันทึกในไฟล์ของแต่ละ agent ไม่มีรหัสอ้างอิงข้ามไฟล์ | ใช้รหัสข้อบกพร่องร่วม (เช่น BUG-001) และอ้างจากช่องตรวจรับ |
| ความเป็นอิสระของผู้ตรวจ | ไม่ระบุว่าผู้ตรวจต้องเป็นคนละ agent กับผู้พัฒนา | ระบุข้อกำหนดนี้ (ถ้า `AGENTS.md` ยังไม่มี) |
| เจ้าของไม่ตอบ | งานจำนวนมากรอการยืนยันจากเจ้าของโครงการ (0a.1 รวม 14 รายการ) ถ้าไม่ตอบ โครงการหยุดทั้งหมด | ตั้งกรอบเวลาและค่าเริ่มต้น: ถ้าไม่ตอบภายใน N วันให้ใช้ค่าที่ Concept เสนอและทำเครื่องหมายเป็น "สมมติฐานรอยืนยัน" |
| Regression | มีเฉพาะใน Gate 3 | ให้ทุก Gate ระบุว่าต้องผ่านชุดทดสอบของ Gate ก่อนหน้าซ้ำทั้งหมด |
| เวอร์ชัน | ไม่มีบันทึกการแก้ Checklist | เพิ่มเลขรุ่นและบันทึกการเปลี่ยนแปลงท้ายไฟล์ |

#### R21 · รายการ "3.1 Sandbox/ZIP" ไม่มีที่มาใน Concept

หัวข้อ "ประเด็นที่ต้องยืนยัน" ระบุ "Sandbox/ZIP เป็นตัวเลือกนอก Roadmap" แต่ Concept v2 ไม่มีคำนี้เลย Phase 3 ใน Concept คือ Cloud Sync, PWA, Localization ควรระบุที่มา (เอกสารหรือการตัดสินใจใด) หรือถอดออก ถ้ายังต้องการเก็บไว้ น่าพิจารณาว่าตัวเลือกแบบ ZIP อาจเป็นทางสำรองสำหรับเบราว์เซอร์ที่ไม่รองรับ File System Access API ซึ่ง Phase 1 (`1.1`) ตั้งใจแค่แจ้งว่าไม่รองรับ จึงควรตัดสินก่อน Phase 3 ถ้าจะใช้เพื่อเหตุผลนี้

#### R22 · Concept กับ Checklist เริ่มเหลื่อมกัน

| จุด | Concept | Checklist |
|---|---|---|
| Gate 0a | Parity กลุ่ม A = 100% (§4.2) | A และ A+ ตรงกัน 100% พร้อม SDK/fixture ตรึงและ baseline |
| งานใน 0a | Undo/Redo เป็นข้อพิจารณาใน §3.12 | เป็นเกณฑ์ตรวจรับของ `0a.3` |
| 3.1 | ไม่มี Sandbox/ZIP | มี (R21) |

ไม่ผิดที่ Checklist เข้มกว่า แต่ควรเลือกเอกสารหนึ่งฉบับเป็นต้นทางและปรับอีกฉบับให้ตรง โดยเสนอให้ **Concept เป็นสเปก** และ **Checklist เป็นแผนตรวจรับ** แล้วอัปเดต Concept §4.2 ให้ตรงกับ Gate ที่ตั้งใจใช้จริง

## 6. คำถามที่ต้องให้เจ้าของโครงการตัดสิน

1. ตารางเวลา Phase 0a ~2 สัปดาห์ สมเหตุสมผลกับจำนวนผู้พัฒนาจริงหรือไม่ และยอมให้แยกงานที่ไม่ใช่ Parity ออกจาก Gate 0a หรือไม่ (R7)
2. เมื่อ hash ของไฟล์ที่ระบบสร้างต่างไป ผู้ใช้ควรทำอะไรได้บ้าง (S3)
3. ภาษาของ UI ใน MVP คือภาษาใด (S7)
4. ที่มาของรายการ Sandbox/ZIP คืออะไร และต้องการให้อยู่ใน Roadmap หรือไม่ (R21)
5. ถ้าไม่ตอบภายในกรอบเวลา ยอมให้ใช้ค่าที่ Concept เสนอเป็นสมมติฐานชั่วคราวหรือไม่ (R20)
6. ผู้ใช้เป้าหมายใช้ระบบปฏิบัติการใดเป็นหลัก เพื่อกำหนดว่า CI ต้องรันบน Windows เป็นอย่างน้อยหรือไม่ (R17)

## 7. ลำดับที่แนะนำ

1. ตอบคำถามข้อ 1–6 ข้างต้น
2. ทำ `0a.0` (spike) ก่อนตัดสินใจเรื่องวิธีเก็บ Trace ใน `0a.1`
3. ปิด `0a.1` รวมประเด็นสเปกใน R6 และ S1–S3
4. แก้ Checklist ตามข้อ 4 แล้วให้ Gemini และ GPT ตรวจรับรองเหมือนรอบ Concept v2
5. จึงเริ่ม `0a.2` (Contract + fixture + รายการกฎ)

**สิ่งที่ Checklist ทำได้ดีและควรคงไว้:** การแยกช่อง "พัฒนา" ออกจาก "ตรวจรับ", การผูกเกณฑ์ตรวจรับกับกลุ่มทดสอบ A–D, การใส่ Gate ปิดทุก Phase, การให้ขอการยืนยันก่อนเพิ่มงานนอก Checklist และการเว้น Phase 3 ไว้ทำ checklist แยกรายฟีเจอร์
